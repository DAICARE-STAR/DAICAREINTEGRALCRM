# platform — integracion

Repo leído: Huly Platform (hcengineering/platform), licencia EPL-2.0 según las cabeceras de los archivos revisados. Todas las rutas son relativas a la raíz del repo. Solo lectura; nada se copió.

## Cómo lo resuelve (hechos, cada uno con su cita ruta/relativa/archivo:línea)

1. **API REST sobre el mismo núcleo de transacciones que usa la interfaz.** El transactor expone `GET /api/v1/find-all/:workspaceId`, `POST /api/v1/tx/:workspaceId`, `GET /api/v1/search-fulltext/:workspaceId`, `POST /api/v1/request/:domain/:workspaceId`, `GET /api/v1/load-model/:workspaceId` y `GET /api/v1/account/:workspaceId`. No es CRUD por recurso: es consulta genérica por clase más envío de transacciones. Cita: `pods/server/src/rpc.ts:263` (find-all), `:295` (tx), `:337` (account), `:344` (load-model), `:377` (search), `:406` (request). El `POST /event` está marcado como obsoleto a favor de `tx` (`pods/server/src/rpc.ts:324-326`). No hay GraphQL propio; GraphQL solo aparece en el conector de GitHub (`services/github/github.graphql`).
2. **Cliente REST con control de cuota en el cliente.** El cliente lee `X-RateLimit-Limit/Remaining/Reset`, se frena cuando queda menos de un tercio de la cuota y reintenta con espera. Cita: `foundations/core/packages/api-client/src/rest/rest.ts:159` (checkRate), `:174` (updateRateLimit), `:180` (checkRateLimits). El servidor emite esas cabeceras y `Retry-After` en `pods/server/src/rpc.ts:66-77`.
3. **Respuestas con ETag y compresión negociada.** El cuerpo JSON se hashea (sha256) para devolver 304 y se comprime con snappy o gzip según `accept-encoding`. Cita: `pods/server/src/rpc.ts:89-99` (ETag y 304) y `:105-127` (compresión).
4. **Tokens de API por usuario y espacio de trabajo, revocables, con tope.** `createApiToken` exige nombre (máx. 255), vigencia de 1 a 365 días, rol mínimo User, prohíbe crear tokens desde un token de API, aplica tope por cuenta contando solo los vigentes y guarda el registro (revocados y vencidos se conservan como auditoría). Cada petición con token de API consulta la tabla y rechaza si está revocado o vencido. Cita: `server/account/src/operations.ts:2750-2818` (alta), `:2735-2739` (no encadenar tokens), `server/account/src/utils.ts:276-283` (revocación verificada en cada llamada), `server/account/src/types.ts:173-183` (modelo ApiToken).
5. **Tokens de solo lectura.** El token puede llevar `extra.readonly`; el servicio de exportación lo rechaza en operaciones que escriben. Cita: `services/export/pod-export/src/server.ts:310` y `:508`. El middleware de transacciones además bloquea toda escritura a los roles `DocGuest` y `ReadOnlyGuest`: `foundations/server/packages/middleware/src/guestPermissions.ts:136-138`.
6. **Webhooks: solo entrantes y solo de pasarelas de pago.** El servicio de pagos recibe webhooks de Stripe y Polar, verifica la firma con el secreto sobre el cuerpo crudo (400 sin firma, 403 con firma inválida) y procesa los eventos de suscripción y factura sin bloquear la respuesta. Cita: `services/payment/pod-payment/src/providers/stripe/webhook.ts:41-64` (firma) y `:69-81` (enrutado por tipo de evento). La búsqueda de `webhook` en el repo no halló webhooks salientes configurables por el cliente; la integración hacia afuera es por la API REST o por los conectores.
7. **Exportación a CSV y JSON, sin Excel.** El servicio de exportación acepta solo `json` y `csv` (`services/export/pod-export/src/server.ts:258`), con dos modos: asíncrono (`POST /exportAsync`, línea 290: responde "Export started", genera un zip, lo guarda en el Drive del usuario y envía un aviso, líneas 352-364) y síncrono (`POST /exportSync`, línea 389). El CSV toma la unión de todas las claves como encabezados, ordenadas (`services/export/pod-export/src/csv/csv-serializer.ts:34-39`) y los adjuntos van a una carpeta `files/` referenciada desde la columna `attachments` (`:61-63`). No hay ningún archivo `.xlsx` ni biblioteca de hojas de cálculo en el repo.
8. **Exportación con transformación configurable.** `TransformConfig` permite omitir atributos, renombrar claves y aplicar transformaciones por atributo; los arreglos se reducen a su longitud por defecto. Cita: `plugins/export/src/types.ts:62-66`, `services/export/pod-export/src/transformer.ts:26-70`. Hay además copia entre espacios de trabajo con estrategia de conflicto `skip` o `duplicate` y mapeadores de campos: `services/export/pod-export/src/server.ts:457-500`.
9. **Importación por un modelo intermedio, no por CSV genérico.** El importador convierte cada origen (Notion en Markdown y CSV, ClickUp en CSV, DOCX, un YAML propio "Unified Huly Format") a una estructura `ImportWorkspace` y la inserta con un solo motor. Cita: comandos en `dev/import-tool/src/index.ts:135` (Notion), `:166` (ClickUp), `:182` (formato Huly); motor en `packages/importer/src/importer/importer.ts:273` (WorkspaceImporter) y `:1383-1425` (documentos unificados creados con `createDoc` o `addCollection`, conservando el `_id` si viene, línea 1394).
10. **El importador de ClickUp es el patrón de migración desde otra herramienta.** Lee el CSV con `csvtojson`, arma proyectos y estados a partir de las columnas, vincula tareas hijas por `Parent ID` y falla si falta el padre. Los usuarios se mapean por nombre completo y los autores de comentarios por correo; lo que no se encuentra queda como comentario de texto. Cita: `packages/importer/src/clickup/clickup.ts:116` (lectura), `:141-173` (jerarquía; errores en `:163` y `:173`), `dev/import-tool/docs/clickup/README.md` secciones "User Mapping" y "Limitations".
11. **Esquema declarativo con validación para el formato de importación.** Cada tipo de entidad declara campos obligatorios y opcionales con tipos de campo (`ConstantFieldType`, `OneOfFieldType`, ruta existente, propiedad con `label`/`type`/`enumOf`/`refTo`). Cita: `packages/importer/src/huly/schema.ts:16-105` (tipos de campo y esquema de propiedad), `:110-130` (esquemas de Association, Enum, MasterTag).
12. **Sincronización de correo por Gmail con push.** El pod de Gmail hace una sincronización inicial, luego registra un `watch` contra un tema de Pub/Sub y lo renueva cada 24 horas; limita la tasa con un contador propio. Cita: `services/gmail/pod-gmail/src/gmail.ts:575-588` (arranque y renovación), `:734-745` (watch), `services/gmail/pod-gmail/src/rateLimiter.ts`.
13. **Sincronización de calendario incremental con token de sincronización.** Usa `syncToken` de Google, pagina, ante 410 descarta el token y resincroniza completo, y guarda el último token por usuario y calendario. Cita: `services/calendar/pod-calendar/src/sync.ts:233-268` (eventos) y `:627-665` (lista de calendarios); notificaciones push en `services/calendar/pod-calendar/src/main.ts:135-158`. También existe una opción CalDAV a nivel de configuración (`plugins/calendar/src/index.ts:185`, `:309`).
14. **Hilos de correo por Message-ID.** Un servicio de correo común mantiene un mapa (almacén clave-valor) de `mailId` a hilo (una Card) y resuelve el padre por `inReplyTo`. Cita: `services/mail/mail-common/src/thread.ts:56-66` y `:102-112`; forma del mensaje en `services/mail/mail-common/src/types.ts:35-48`. Envío saliente por SMTP con `nodemailer`, con transportes por remitente en caché: `services/mail/pod-mail/src/transport.ts:65-76`, `services/mail/pod-mail/src/mail.ts:47-52`, endpoint `/send` en `services/mail/pod-mail/src/main.ts:52`.
15. **Acceso de externos: enlaces públicos y roles de invitado.** Un `PublicLink` guarda URL, ubicación dentro de la app, un objeto `restrictions` (solo lectura, sin comentarios, sin navegación, sin acciones), un indicador de revocable y el documento al que apunta. Cita: `models/guest/src/index.ts:10-17`, `plugins/guest/src/index.ts:16-21`. La escala de roles incluye `ReadOnlyGuest`, `DocGuest`, `Guest`, `User`, `Maintainer`, `Owner`, `Admin` (`foundations/core/packages/core/src/classes.ts:605-613`). Los permisos del invitado se definen por clase y el middleware los aplica (`foundations/server/packages/middleware/src/guestPermissions.ts:48-92`, `:287-315`). El ingreso anónimo como invitado se desactiva con `DISABLE_GUEST_LOGIN` (`server/account/src/operations.ts:158-176`). No es un portal de clientes con identidad propia: es acceso a la misma aplicación con permisos recortados.
16. **Identidad de contacto desacoplada del valor.** Una persona tiene varios `SocialId` con tipo (email, teléfono, Google, Telegram, GitHub, OIDC), id generado independiente del valor, verificación y borrado lógico; los canales (`Channel`) cuelgan del contacto con un proveedor. Cita: `foundations/core/packages/core/src/classes.ts:1002-1026`, `plugins/contact/src/index.ts:50-85`. Las integraciones de cada usuario y sus secretos se guardan en tablas separadas por tipo (`server/account/src/types.ts:200-217`).
17. **Internacionalización por archivo JSON por plugin y por idioma, con respaldo en inglés.** Cada plugin trae `lang/<idioma>.json`; hay 14 idiomas en los plugins revisados, entre ellos `es`. Los textos se piden con identificadores (`IntlString`) y la traducción cae a inglés si falta la clave. Cita: `plugins/contact-assets/lang/es.json:1-12`, `foundations/core/packages/platform/src/i18n.ts:141-170` (respaldo a `en`), `server/server-pipeline/src/internationalization.ts:85-127` (registro de cargadores en el servidor), `server/account/lang/es.json` (mensajes del servicio de cuentas). Formato de mensajes ICU con `IntlMessageFormat` (`i18n.ts:35`).
18. **Traducción automática como servicio aparte y de pago.** Un servicio `translate` mantiene por espacio de trabajo la lista de idiomas destino y usa un cliente de OpenAI para traducir mensajes de chat; reporta consumo de tokens a facturación. Cita: `services/translate/src/conroller.ts:40-80`, `services/translate/src/billing.ts`.
19. **Conector bidireccional con GitHub.** Sincroniza issues, PR, comentarios y revisiones en ambos sentidos; el propio README lista trabajo pospuesto y limitaciones de campos personalizados. Cita: `services/github/pod-github/src/sync/issues.ts`, `services/github/readme.md:1-12`. Es el ejemplo de lo costoso que resulta mantener un espejo bidireccional.

## Decisiones de diseño que se notan y su porqué

- **API genérica sobre el modelo de transacciones, no un recurso REST por entidad.** Todo se consulta por clase con un filtro en JSON y todo se escribe como transacción. Gana una sola superficie para todos los módulos y el mismo control de permisos que la interfaz. Pierde: la API no se describe sola; el cliente debe conocer clases y atributos (por eso baja el modelo con `load-model`). Evidencia: `pods/server/src/rpc.ts:263-295`, `:344`.
- **Cuotas visibles para el cliente.** Cabeceras estándar y cliente que se autorregula: se trata la API como producto para integradores y no solo como canal interno.
- **Token de API acotado y auditable.** No puede crear tokens, tiene tope por cuenta, vence a lo sumo en 365 días y la revocación se verifica en cada llamada; los revocados se conservan como auditoría (comentario en `server/account/src/operations.ts:2792-2793`). Prioriza el control sobre la comodidad del integrador.
- **Un formato intermedio para importar.** En lugar de un importador por origen contra la base, cada origen produce el mismo modelo y un motor lo inserta. Reduce el costo de añadir un origen; el precio es que el modelo sigue la forma de las entidades de Huly (proyectos, teamspaces, issues), que a una pyme no le sirven tal cual.
- **Integraciones externas como servicios separados que hablan con la API.** Gmail, calendario, correo, GitHub, Telegram y traducción son pods independientes con su propia cuota y estado; el transactor no los conoce. Aísla fallos y permite activarlos por instalación, a costa de más piezas desplegables.
- **El valor de contacto no es la clave.** Los registros referencian el id generado del `SocialId`, así que cambiar un correo no rompe el historial (comentario en `foundations/core/packages/core/src/classes.ts:1014`). Es relevante para cualquier CRM con histórico de correos.
- **Portal externo como recorte de permisos, no como aplicación aparte.** Reutiliza la aplicación y limita por rol y por restricciones del enlace; ahorra una segunda interfaz, pero expone la misma superficie de API con filtros por middleware.
- **Textos como recurso por plugin con respaldo a inglés.** Cada módulo aporta sus traducciones, así un módulo a la carta trae sus propios idiomas.

## Adoptable para Bash Logistics (lista numerada A1, A2…: la idea, la cita que la respalda, por qué le sirve a una pyme, y el esfuerzo estimado bajo, medio o alto sobre Postgres con RLS y React)

- **A1. Tokens de API por usuario y por instalación, con vigencia, revocación verificada en cada llamada y tope por cuenta.** Cita: `server/account/src/operations.ts:2750-2818`, `server/account/src/utils.ts:276-283`, `server/account/src/types.ts:173-183`. Le sirve porque el contador o el integrador de la pyme conecta una hoja de cálculo o un sistema de facturación sin compartir su contraseña. En Postgres: tabla `api_tokens` con hash del token (nunca el token), `expires_at`, `revoked_at` y `scopes`; una Netlify Function verifica el hash y toma el rol del miembro dueño para que RLS siga aplicando. Esfuerzo: medio.
- **A2. Alcance de solo lectura en el token.** Cita: `services/export/pod-export/src/server.ts:310`, `foundations/server/packages/middleware/src/guestPermissions.ts:136-138`. Le sirve para entregar un acceso a un contador o a una herramienta de BI sin riesgo de escritura. En Postgres: un rol de base de solo lectura o una política RLS que exija `scope = 'read'` para INSERT, UPDATE y DELETE. Esfuerzo: bajo si se hace junto con A1.
- **A3. Cabeceras de cuota y `Retry-After` en las Netlify Functions públicas.** Cita: `pods/server/src/rpc.ts:66-77`, `foundations/core/packages/api-client/src/rest/rest.ts:159-200`. Le sirve para que una integración mal hecha no tumbe la instalación de un cliente. Las funciones no tienen estado compartido: la cuota requiere un contador en Postgres o un almacén externo. - **A4. Exportación a CSV con encabezado calculado, transformación por columna y entrega asíncrona con aviso.** Cita: `services/export/pod-export/src/csv/csv-serializer.ts:30-48`, `services/export/pod-export/src/transformer.ts:26-70`, `services/export/pod-export/src/server.ts:290-364`. Le sirve porque lo primero que pide una pyme es "sácame esto a Excel". Esfuerzo: bajo para exportación síncrona de listas pequeñas; medio para la asíncrona (función en segundo plano de Netlify, Storage para el archivo y el módulo de avisos que ya existe). Hay que escribir el CSV con BOM UTF-8 y separador configurable para que Excel en Latinoamérica lo abra bien; el repo no resuelve esto y no ofrece `.xlsx`.

## No conviene copiar (y por qué)

- **La API genérica por clase con consulta JSON y transacciones.** Depende del modelo reflexivo de Huly (clases, jerarquía, mixins) que el cliente carga entero. Bash Logistics ya tiene Postgres con RLS y la API de Supabase, que cumple esa función; construir otra capa duplicaría. Ver `pods/server/src/rpc.ts:263-295`.
- **El formato "Unified Huly Format" en YAML.** Sigue la forma de las entidades de Huly (teamspaces, proyectos, issues, tarjetas) y no tiene equivalente en un ERP. Se reutiliza la idea de esquema declarativo (A5), no el formato.
- **El conector bidireccional de GitHub.** El propio README lista limitaciones y trabajo pospuesto; mantener espejos bidireccionales es el costo más alto y menos rentable para una pyme. Ver `services/github/readme.md:1-12`.
- **La arquitectura de más de 30 servicios con Redpanda, Elasticsearch, CockroachDB y MinIO.** Está descrita en `ARCHITECTURE_OVERVIEW.md:7-97`; no cabe en una instalación por cliente de bajo costo.
